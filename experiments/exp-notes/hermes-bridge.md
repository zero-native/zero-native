# Hermes V1 C++ JNI Bridge Notes (zero-native)

Detailed findings, header locations, config flags, and gotchas discovered while building the standalone Hermes V1 JNI bridge on Android (tested on Lava Blaze 2 5G, Android 13/14, MediaTek Dimensity 6020).

---

## 1. Headers & CMake Prefab Packages

- **CMake Prefab Package Name:** In `com.facebook.hermes:hermes-android:250829098.0.17`, the package generated by AGP's Prefab is `hermes-engine`, NOT `hermes`.
  ```cmake
  find_package(hermes-engine REQUIRED CONFIG)
  target_link_libraries(zn PRIVATE hermes-engine::hermesvm)
  ```
- **JSI Vendoring:** `hermes-android` does NOT package JSI headers or `libjsi.so`. We vendor `libjsi.so` (arm64-v8a) and the JSI C++ headers (`jsi.h`, `jsi-inl.h`, `hermes-interfaces.h`) extracted from `com.facebook.react:react-android:0.87.1` AAR.
- **C++ Compiler Flags:** Must compile with `-std=c++20`, `-frtti`, and `-fexceptions` because JSI relies on C++ exception handling (`facebook::jsi::JSError`).

---

## 2. Runtime Configuration & Microtask Queue

In `hermes/Public/RuntimeConfig.h`:
```cpp
/* Support for using microtasks. */
F(constexpr, bool, MicrotaskQueue, false)
```
- **Gotcha:** `MicrotaskQueue` defaults to `false` in Hermes!
- **Fix:** In order for Promises and microtasks to drain predictably after each host dispatch, `RuntimeConfig` must explicitly enable `MicrotaskQueue`:
  ```cpp
  ::hermes::vm::RuntimeConfig config = ::hermes::vm::RuntimeConfig::Builder()
      .withMicrotaskQueue(true)
      .build();
  auto runtime = facebook::hermes::makeHermesRuntime(config);
  ```
- **Drain Microtasks:** Call `runtime->drainMicrotasks()` after every evaluation, event dispatch, and timer execution.

## 3. Host Functions Installed on JS `global`

Installed via `facebook::jsi::Function::createFromHostFunction`:
1. `__zn_flush(opsJson: string)`:
   - Dispatches op batches from the JS thread to Kotlin `NodeStore.applyBatch(opsJson)` posted to `Looper.getMainLooper()`.
2. `__zn_log(level: number, msg: string)`:
   - Routes to Android `__android_log_print` with tag `zn`.
3. `__zn_setTimeout(id: number, delayMs: number)` & `__zn_clearTimeout(id: number)`:
   - Hermes has **no native timers**.
   - JS tracks integer IDs. Native schedules `Handler.postDelayed` on the `zn-js` Looper, calling `__zn_timerFired(id)` when elapsed.
4. `__zn_now()`:
   - Reads hardware monotonic clock via `clock_gettime(CLOCK_MONOTONIC, &ts)` with microsecond resolution, completely bypassing JNI overhead.

## 4. JNI & Threading Gotchas

1. **Kotlin `object` (Singleton) JNI Calling Convention:**
   - In Kotlin, functions declared inside an `object` without `@JvmStatic` pass `jobject thisObj` (the singleton instance), NOT `jclass clazz`.
   - Passing `clazz` directly to `env->GetStaticMethodID` triggers:
     `JNI DETECTED ERROR IN APPLICATION: jclass has wrong type ... in call to GetStaticMethodID`.
   - **Fix:** Annotate native methods with `@JvmStatic` AND use `env->FindClass("dev/zeronative/exp2/ZnBridge")` to obtain a global reference to the class.
2. **JSI `Function::call` Overload Ambiguity:**
   - Passing an array like `facebook::jsi::Value args[3]` to `fn.call(rt, args, 3)` matches the template `call<Value(&)[3], int>` rather than `call(rt, const Value*, size_t)`, causing a static assertion error.
   - **Fix:** Pass values directly to the variadic template: `fn.call(rt, Value(nodeId), String::createFromUtf8(rt, event), ...)`.
3. **Main Thread Never Waits for JS:**
   - `HandlerThread("zn-js")` handles all Hermes execution.
   - Taps and lifecycle events are posted asynchronously to `jsHandler`.
   - Op batches are posted asynchronously to `mainHandler`.
